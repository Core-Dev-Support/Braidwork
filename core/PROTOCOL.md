# Спецификация протокола Braidwork

Версия схемы: `0.1`
Статус: черновик, изменение только через D-решения в `DECISIONS.md`

Документ независим от языков реализации. Клиенты на Kotlin, ArkTS, C# и C генерируют схему из этого репозитория, а не пишут её сами.

---

## 1. Назначение и границы

Протокол связывает устройства в семью и передаёт между ними данные пользователя: буфер обмена, файлы, изображения, уведомления, поток экрана, ввод, состояние мультимедиа и адреса для обнаружения.

Протокол не обеспечивает:

- доступ к аккаунтам, паролям и данным приложений вне механизмов, которые ОС предоставляет явно;
- обход ограничений операционной системы;
- работу без согласия владельца устройства — каждое устройство должно явно получить ключ через сопряжение.

## 2. Модель идентичности

### 2.1 Ключи устройства

При создании устройство генерирует три ключа:

| Ключ | Алгоритм | Назначение |
|---|---|---|
| `static` | X25519 | Noise XX, шифрование канала |
| `signing` | Ed25519 | Подпись заявлений о доверии |
| `qr` | X25519 | Однократный bootstrap при сканировании |

Один и тот же `static` ключ участвует и в Noise XX, и в согласовании.

### 2.2 Идентификатор

```
device_id = base32_nopad( blake3( "bw-device-id-v1" || signing_public )[0..16] )
```

Отпечаток для сверки человеком — четыре группы по четыре символа из того же хэша.

Идентификатор вычисляется, а не выдаётся, поэтому он стабилен между перезагрузками и не может быть занят другим устройством.

### 2.3 Семья

Семья — граф доверия. Устройство, введённое устройством `A`, получает заверение `A` и доступ к открытым ключам всех, кому `A` доверяет. Корнем считается устройство, выполнившее первое сопряжение, но корень не имеет технических привилегий: он может отозвать только то, что заверено им самим.

Полное описание семьи — список корней и заверений. Списки расходятся и синхронизируются gossip-сообщениями.

### 2.4 Ввод устройства в семью

1. Устройство `B` показывает QR, содержащий `qr_public` устройства `A` плюс одноразовый токен.
2. `B` сканирует QR. Между ними выполняется Noise XX с временным ключом из QR.
3. `B` отправляет `join_request` со своим `device_id`, `signing_public`, списком возможностей и подписью.
4. `A` отвечает `join_response`: подписанное заверение на `B` плюс заверения на всё, чему `A` доверяет, ограниченные политикой.
5. `B` проверяет подпись, сохраняет заверения, и с этого момента входит в семью.
6. Одноразовый токен истекает через 120 секунд и не может быть переиспользован.

QR не является постоянным. Повторное сканирование ничего не меняет: устройство узнаётся по ключу и уже доверяет само себе.

### 2.5 Отзыв

`revoke` — подписанное заявление, что `device_id` больше не участвует. Рассылается gossip-сообщением `revoke_notice`. Устройства, получившие его, удаляют заверения и сессионные ключи, а при следующем обнаружении отвергают устройство.

Ключи отзыва не нужны, потому что само устройство не принимается. Компрометация закрытого ключа на чужом устройстве требует ротации `signing`, что задаётся сообщением `key_rotate` от того же устройства.

## 3. Транспорт

### 3.1 Интерфейс

Одна абстракция `Transport` с реализациями:

| Реализация | Среда | Скорость | Роль |
|---|---|---|---|
| `LanTransport` | общая сеть, mDNS | высокая | основной в домашнем сценарии |
| `SoftApTransport` | точка доступа на телефоне | высокая | когда роутера нет |
| `UsbTransport` | туннель через кабель | максимальная | самый быстрый резерв |
| `BleTransport` | Bluetooth LE | низкая | bootstrap, heartbeat, gossip |
| `IceTransport` | интернет, ICE со STUN | средняя | разные сети |

### 3.2 Выбор канала

Каналы ранжируются по измеренной пропускной способности, задержке и расходу батареи. Выбирается лучший доступный; при деградации — следующий. Переключение не разрывает сессию: она привязана к логическому соединению, а не к каналу.

BLE используется как heartbeat-канал: он держит адреса актуальными и прогревает туннель, чтобы переключение ощущалось мгновенным.

### 3.3 Обнаружение

**LAN.** mDNS-сервис `_family._udp` с TXT-записью: версия протокола, `device_id`, список возможностей, наличие публичного адреса, короткий отпечаток.

**BLE.** Рекламное поле Manufacturer Data: версия, `device_id`, полный список возможностей. Отдельно — advertising-пакет без данных о семье, для режима «я рядом».

**Вне сетей.** Автоматическое обнаружение невозможно. Обмен выполняется через rendezvous: устройство пользователя с публичным адресом или любой публичный TURN. Данные через посредника не идут, он только помогает завершить ICE-рукопожатие.

**Акустика.** Bootstrap по микрофону и динамику: устройства обмениваются ключами и адресами на расстоянии десятков метров. Только начальная настройка, данные затем идут по сети.

### 3.4 ICE

Используется стандартный ICE, как в WebRTC. Кандидаты собираются из всех локальных интерфейсов и отправляются в `candidate_offer`. Ответчик присылает свои. Проверка пар начинается с UDP на LAN, затем ICE. При невозможности прямого соединения — TURN.

Собственный STUN-сервер продукта не разворачивается и не требуется.

## 4. Формат сообщений

Все сообщения — Protocol Buffers, схема в `proto/braidwork/v1/braidwork.proto`, пакет `braidwork.v1`.

### 4.1 Заголовок кадра

```
magic:   2 байта, 0x42 0x57   ("BW")
version: uint8,  1
kind:    uint8,  тип сообщения из MessageKind
flags:   uint16, битовые флаги
length:  uint32, длина protobuf-тела
payload: length байт
```

`kind` и `version` читаются без полного разбора тела, чтобы незнакомые типы отбрасывались дёшево.

### 4.2 Флаги

Значения совпадают с `FrameFlags` в схеме.

- `0x0001` — сжатие (zstd), тело после заголовка.
- `0x0002` — ожидается подтверждение.
- `0x0004` — продолжение составного сообщения.
- `0x0008` — последний фрагмент составного сообщения.
- `0x0010` — сообщение внутреннее, не пересылается дальше по mesh.

## 5. Типы сообщений

### 5.1 Рукопожатие

- `hello` — заявление `device_id`, подпись, nonce, список возможностей, версия протокола.
- `hello_ack` — принято, подтверждённый список возможностей, отпечаток для сверки.
- `join_request` / `join_response` — ввод в семью, раздел 2.4.
- `revoke_notice` — отзыв устройства.
- `key_rotate` — новая пара `signing` с подписью старой.

### 5.2 Обнаружение и поддержание

- `heartbeat` — время, заряд, текущий канал, измеренная скорость.
- `candidate_offer` / `candidate_reply` — кандидаты ICE.
- `route_preference` — устройство сообщает, какой канал для него дешевле.
- `bye` — штатное завершение сессии с указанием причины.

### 5.3 Данные

- `clipboard_set` — хэш содержимого, MIME-типы, размер, флаги чувствительности. Тело отдельным сообщением при необходимости.
- `clipboard_request` — запрос содержимого по хэшу от конкретного устройства.
- `clipboard_content` — тело, только в ответ на запрос.
- `file_offer` — манифест: список блоков, хэши, размеры, общий хэш.
- `file_block` — один блок файла.
- `file_request` — докачка недостающих блоков.
- `gallery_delta` — новые и удалённые снимки с дедупликацией по хэшу.

### 5.4 Оповещения и мультимедиа

- `notification_post` — приложение, заголовок, текст, `android_key`, категории, действия.
- `notification_dismiss` — снятие уведомления на источнике.
- `notification_action` — действие, выбранное на другом устройстве.
- `media_state` — источник, трек, состояние, громкость.

### 5.5 Экран и ввод

- `screen_offer` — параметры кодировщика: разрешение, битрейт, кодек, профиль.
- `screen_start` / `screen_stop` — управление сессией.
- `video_frame` — кадр или фрагмент потока, с индикатором интерактивности.
- `input_event` — тип ввода, координаты, серийный номер для дедупликации.

Поток видео идёт отдельным каналом с собственными параметрами, чтобы не блокировать сообщения управления.

### 5.6 Capability negotiation

`hello` несёт список возможностей. Ответчик пересекает списки и в `hello_ack` возвращает итоговый. Если возможность не согласована, отправитель обязан не использовать соответствующие сообщения, а получатель — молча их игнорировать. Это позволяет добавлять функции без синхронизации версий.

## 6. Идентификаторы в сообщениях

Везде, где поле называется `origin`, это `device_id` отправителя, а не имя и не серийный номер. Имена — только в поле `display_name`, и оно исключительно для интерфейса.

## 7. Ограничения и таймауты

| Параметр | Значение |
|---|---|
| Срок одноразового токена QR | 120 с |
| Heartbeat | 30 с |
| Таймаут сессии без heartbeat | 90 с |
| Повтор отправки при отсутствии подтверждения | 3 раза, с удвоением интервала |
| Максимальный размер фрейма | 1 МиБ |
| Максимальный размер блока файла | 256 КиБ |

## 8. Устойчивость к обрыву

Каждое соединение имеет `session_id`, живущий дольше, чем любой канал. Переключение транспорта создаёт новый канал под тем же `session_id`, поэтому состояние приложения не теряется.

Сообщения внутри сессии защищены от повторов счётчиком окна. Отправитель хранит неотправленные окном, получатель — номера вне окна. Переотправка после переключения канала безопасна.

## 9. Обратная совместимость

- Поле `version` в заголовке обязательно.
- Неизвестные поля protobuf пропускаются.
- Неизвестные типы сообщений игнорируются без ответа.
- Удаление или изменение смысла поля требует нового номера поля и новой версии протокола.
- Обязательные для безопасности поля — только на добавление.

## 10. Что не входит в версию 0.1

- Синхронизация сообщений мессенджеров сверх relay уведомлений.
- Зеркало экрана десктопа на телефоне.
- Передача управления вводом на HarmonyOS NEXT.
- Любая форма push через внешние сервисы.
