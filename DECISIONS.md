# Архитектурные решения

Документ фиксирует решения по открытым вопросам. Решение считается принятым, когда здесь есть запись. Изменение решения — новая запись с датой, а не правка старой.

---

## D-000. Название продукта

**Решение.** Braidwork. Плетение — метафора продукта точная: из отдельных нитей получается полотно, ровно как из отдельных устройств семья.

**Проверка занятости.** Свободно в crates.io, npm, GitHub, а также домены `.app` и `.dev`. Занят `.com`. Смысловых совпадений в той же области не найдено: существующие проекты под этим именем относятся к веб-краулингу, привязке Docker-образов и вёрстке книг.

**Почему не транслитерация.** Русские транслитерации живут в узкой зоне: либо заняты, либо нечитаемы как бренд. Критерий отбора — понимание по-русски хотя бы наполовину, и плетение этому критерию отвечает.

**Не проверено.** Google Play, AppGallery и F-Droid проверить не удалось: Play отдаёт 404 на страницу поиска, F-Droid адресует по внутренним идентификаторам. Основной канал распространения не проверен ни разу, проверка обязательна до публикации. Товарные знаки в классах 9 и 42 — платный поиск, решается перед запуском.

**Альтернатива отклонена.** `ropework` — тоже чистое имя, но верёвка намекает на физический канал, что вводит в заблуждение про наличие сервера.

## D-001. Границы репозиториев

**Решение.** Ядро — отдельный репозиторий с префиксом `braidwork-core`. Каждая платформа — свой репозиторий `braidwork-android`, `braidwork-windows`, `braidwork-linux`, `braidwork-harmony`, `braidwork-android-legacy`. Спецификация протокола живёт в репозитории ядра и является единственным источником истины.

**Почему.** Сборочные тулчейны Android, MSVC, Rust для Windows и DevEco Studio несовместимы. Общий CI означает, что поломка одной платформы останавливает релиз всех остальных.

**Следствие.** Клиент никогда не содержит собственной копии схемы. Он генерирует код из схемы ядра на конкретную ревизию. Расхождение фиксируется контрактным тестом, а не Review.

**Альтернатива отклонена.** Монорепозиторий с единым CI. Проще синхронизировать, но при 5 платформах и разных тулчейнах это устойчивая потеря времени.

## D-002. Форма границы ядра: C ABI

**Решение.** Ядро компилируется в `cdylib` и `rlib`, наружу отдаёт только стабильный C ABI (`core-ffi`). Биндинги генерируются отдельно для каждого языка: JNI-обёртка для Android, NAPI-обёртка для HarmonyOS, C# P/Invoke для Windows, C-FFI для Linux.

**Почему.** Каждая платформа имеет канонический способ вызова нативного кода, и ни один из них не является общим:

- Android — JNI.
- HarmonyOS NEXT — NAPI (`libace_napi`), а не JavaScript. ArkTS компилируется ArkCompiler'ом и не имеет JS-рантайма.
- Windows — P/Invoke.
- Linux — прямой C-FFI.

UniFFI генерирует Kotlin и Swift-исходники и не покрывает ArkTS. Diplomat ориентирован на JS/TS и не даёт NAPI-обёрток. Оба оставлены как возможные ускорители для конкретного клиента, но не как основа.

**Почему не «просто C ABI вручную».** Он и есть основа. Разница в том, что он версионируется явно: каждая функция помечена стабильностью, удаление проходит через deprecation-цикл. Семантическое версионирование ABI отдельно от версий протокола.

**Следствие.** Формат границы фиксируется в `core-ffi/include/core.h` и проверяется тестом на C-совместимость компиляцией минимального клиента на чистом C.

## D-003. Сериализация: Protocol Buffers для всего, включая BLE

**Решение.** Единая схема `.proto` на протокол, генерация через `prost`. Отдельного бинарного формата для BLE нет.

**Почему.** BLE-пакет ограничен MTU 185–512 байт, и кажется, что protobuf там «жирный». Но реальные сообщения по BLE — это heartbeat и gossip адресов, это 20–60 байт в varint-кодировании. Экономия от bespoke-формата — единицы байт на пакет, которые не решают ничего.

Собственный формат означает вторую реализацию парсинга, которую придётся писать на ArkTS, Kotlin и C# отдельно, плюс историю совместимости, которую придётся поддерживать вечно. Эта цена выше выигрыша в байтах.

**Что действительно экономит трафик.** `bytes` для хэшей вместо строк, `fixed64` для таймстемпов, явный `packed` для повторяющихся полей. Это настройка схемы, а не смена формата.

**Следствие.** Поле `version` в заголовке обязательно. Неизвестные поля пропускаются, неизвестные типы сообщений молча игнорируются.

## D-004. Ядро как библиотека, а не как демон

**Решение.** На мобильных платформах ядро встроено в процесс приложения как shared library. На десктопе — отдельный демон с IPC.

**Почему.** Демон на Android упирается в ограничения фоновых процессов, а приложение с foreground-service уже получило эти права. Демон на десктопе нужен для автозапуска без открытого окна, для трея и для переживания закрытия всех окон.

Оба варианта — один и тот же `core` crate. Расходится только способ запуска и способ доступа к API.

## D-005. Онбординг: минимальный при первом запуске

**Решение.** При первом запуске — только создание пары ключей и QR для связки. Никаких длинных объяснений.

Настройка фоновой работы — отдельный экран с чек-листом по бренду, который предлагается заполнить, но не блокирует использование.

**Почему.** Требование отключить оптимизацию батареи — это то, где чаще всего бросают установку. Если поставить его на путь первого запуска, конверсия в пользу упадёт. Если спрятать — половина пользователей потом скажет «не работает».

Компромисс: показать сразу после первого успешного обмена данными, то есть когда человек уже увидел пользу и у него есть мотивация доделать настройку.

## D-006. Дистрибуция: собственный APK без GMS-зависимостей

**Решение.** Клиент не использует Google Play Services. Уведомления приходят по BLE/LAN/gossip, поэтому FCM не нужен. Дистрибуция: свой репозиторий, F-Droid, GitHub-релизы.

**Почему.** Без GMS-зависимостей один и тот же APK работает на Android 5, на Huawei с AOSP и на устройствах без Google-сервисов. Разница только в способе доставки обновлений.

**Уточнение к исходному предложению.** «Разницы в коде не будет» верно не полностью. HarmonyOS NEXT требует отдельного клиента на ArkTS, потому что там нет ни AOSP, ни возможности запуска APK. Но общая логика и протокол — те же.

**Ограничение по AppGallery.** Публикация там возможна, но правила строже Play: использование AccessibilityService для обхода ограничений фоновой работы идёт вразрез с политикой. Основной канал — собственный репозиторий и F-Droid.

## D-007. Аккаунтов нет

**Решение.** Ни регистрации, ни аккаунта, ни телеметрии. Восстановление семьи после потери всех устройств не предусмотрено.

**Почему.** Любая система аккаунтов — это сервер, а вся ценность продукта в заявлении «ваши данные не покидают вашу сеть». Недоступное восстановление — осознанная плата.

**Пересмотр условия.** Если продукт будет продаваться, а не распространяться, отсутствие аккаунтов мешает лицензиям и подписке. Тогда потребуется отдельный сервер лицензирования, и решение пересматривается как D-008.
